# Eschaton

## Project Overview

Eschaton is a first-person 3D game set inside a pair of counter-rotating O'Neill cylinders in deep space. The player explores two massive enclosed habitats — cylindrical worlds with cities, parks, lakes, and rivers built along the inner wall. The game is built in C++ using bgfx for cross-platform rendering, SDL3 for windowing/input, and EnTT for Entity Component System architecture.

The project is code-first with no visual editor. All scene composition, entity placement, and asset pipelines are defined in code or declarative data files.

The habitat interior is **procedurally generated by an offline Python toolchain** (`tools/CityGenerator/`) that emits engine-ready binary chunks. The generator is deterministic from a seed, so the world is reproducible, regenerable in pieces, and diffable. See `docs/WORLD_PIPELINE.md` for the byte-level format reference.

| World generation | Python 3 + numpy | Offline generator, deterministic from seed |

| Model assets | glTF / glb via **cgltf** | Building prototypes, props, monuments |
| Backdrop bake | Blender (headless) | Orthographic colour plate + height map for the far-side shell |

### Why These Choices

- **bgfx** provides shader portability across all major graphics APIs without writing backend-specific code. Shaders are written in a GLSL-like dialect and compiled via `shaderc` to every target.
- **SDL3** is the latest major version of SDL, handling windowing, input abstraction (keyboard, mouse, gamepad), and platform differences.
- **EnTT** is a header-only, cache-friendly ECS library that is mature, fast, and well-documented. It will be the backbone of all game object management.
- **C++20** for structured bindings, concepts, `std::span`, and other ergonomic improvements. Avoid bleeding-edge C++23 features that may reduce compiler portability.
- **Python for generation, not C++.** Generation is offline and runs once per world revision. Python's iteration speed is worth far more here than runtime performance, and the generator's output is a frozen artifact checked in alongside the seed.
- **Custom binary world data, not glTF, for chunks.** The world is described better by *instance tables* than by meshes: 20 building types with fixed dimensions means ~375k transforms rather than 375k meshes. glTF enters only as the container for the prototype models themselves.

## World Architecture

### The Cylinders

The game world consists of two O'Neill cylinders. Only one cylinder is loaded into memory at a time; the other is the second "level."

| Property | Value |
|---|---|
| Length | 32,000 m (32 km) |
| Circumference | 25,100 m |
| Radius | 3,994.8 m |
| Diameter | 7,989.6 m (nominally "8 km") |
| Hull thickness | ~10 m |
| Interior surface area | ~803 km² per cylinder |
| Rotation | ω ≈ 0.04955 rad/s, period ≈ 126.8 s (~1g at the inner wall) |

> **Reconciliation note.** Earlier drafts specified a 4,000 m radius, implying a 25,132.7 m circumference. The generator uses a circumference of **25,100 m** because it factors cleanly into 50 chunk columns of 502 m, which the seamless wrap depends on. The resulting radius is 3,994.8 m — 5.2 m under the nominal 4 km, which changes ω by 0.05% and is invisible in play. **25,100 m is now canonical.** Do not reintroduce 25,132.7 anywhere; the wrap arithmetic depends on the exact figure.

The cylinders are **fully enclosed** — there is no sky, no windows. The interior is lit by a **central luminous column** running the full 32 km length of the cylinder, suspended along the rotational axis. This column provides the day/night cycle and all ambient light.

The "floor" is the **inner wall** of the cylinder. Gravity points radially outward from the axis of rotation. The player walks on the concave interior surface. Looking up, the landscape curves away and eventually arcs overhead.

### Interior Composition

- **Urban zones** — Haussmann-style city: boulevards between monumental roundabouts, minor street grids, continuous block frontage
- **Green zones** — 7.5% of city superblocks are parkland, plus a 1 km green border at each end of the cylinder, plus riverside parks
- **Water features** — a single river making five helical laps of the circumference (lakes and canals not yet generated)
- **Infrastructure** — bridges carrying boulevards over the river, quay streets along both banks, monument platforms at every roundabout

### Coordinate Systems

Three coordinate spaces exist. Keep them straight; most bugs in the world layer are confusions between them.

**1. Map space** — what the generator and the exported data use.

| Axis | Meaning |
|---|---|
| X | around the circumference, 0 … 25,100 m, **wraps** |
| Y | along the cylinder axis, 0 … 32,000 m, does not wrap |
| Z | up, away from the inner surface (toward the rotation axis) |

**2. Cylindrical world space** — what the ECS stores, in double precision.

```
theta = X / 3994.8              // radians around the circumference
z     = Y                       // metres along the axis
r     = 3994.8 - Z_map          // distance from the axis; ground = 3994.8
```

**3. Camera-relative render space** — single precision, rebased, what the GPU sees.

Because the world is a cylinder, X differences must always take the shortest arc:

```cpp
constexpr double kMapW = 25100.0;
inline double wrap_dx(double dx) { return dx - kMapW * std::round(dx / kMapW); }
inline double wrap_x (double x)  { double m = std::fmod(x, kMapW); return m < 0 ? m + kMapW : m; }
```

This applies to *gameplay* as well as rendering: distance checks, AI perception, audio falloff, nav queries, minimap scrolling.

### Floating Point Strategy: Origin Rebasing

- The world origin is periodically shifted to the player's current position.
- All positions are stored as **double-precision** cylindrical coordinates in the ECS.
- Before rendering, positions convert to **single-precision camera-relative** coordinates.
- float32 quantizes to about 4 mm at 32 km but under a millimetre within a few km of the origin, which is where rebasing keeps everything.

**Chunk identity is separate from chunk placement.** For a viewer in column `c`, place columns `c-k … c+k` at `(c + offset) × 502` and resolve identity with `mod 50`. You never render "column 49 next to column 0" — you render a continuous run around the viewer and let identities wrap underneath. Rebase by shifting every chunk translation by ±502 rather than teleporting the player; exported chunk geometry is chunk-local, so vertex data never changes.

## Physics

### Rotating Reference Frame

The cylinder rotates to produce artificial gravity. Objects inside experience:

1. **Centrifugal acceleration** — acts as "gravity," pointing radially outward. At the inner wall (r = 3994.8 m), this equals ~9.8 m/s².
2. **Coriolis acceleration** — `a_cor = -2ω × v` — deflects moving objects, perpendicular to both the rotation axis and the velocity vector.
3. **Centrifugal gradient** — "gravity" decreases linearly with altitude. At the axis it is zero; at 2,000 m altitude, ~0.5g.

The Coriolis effect is **a core gameplay mechanic**, not a cosmetic detail. It must be perceptible and consistent for thrown objects, projectiles, falling objects, and water flow.

### Coriolis and the River

Earlier drafts cautioned against circumferential rivers on the grounds that Coriolis deflection would look unnatural. The generated river runs at roughly **13° off the circumference** (five laps over 32 km), so that guidance needs restating rather than enforcing:

- **Circumferential flow** puts the Coriolis term in the **radial** direction — it changes apparent weight rather than pushing the water sideways. At 2ω ≈ 0.099 m/s² per m/s, a 2 m/s current running prograde is about 2% "heavier," retrograde about 2% "lighter." Visible as a slight difference in water level against the two banks, not as deflection.
- **Axial flow** is what gets deflected laterally, and only the small axial component (sin 13° ≈ 0.22) contributes.

Net effect: the helical river is physically fine. If the asymmetry is wanted as a visible detail, bias the meander model so bends develop preferentially on one bank — the generator's meander offsets are a single signed array and easy to skew.

### Physics LOD

| Distance from Player | Physics Fidelity |
|---|---|
| 0–200 m | Full Coriolis + centrifugal, per-frame integration |
| 200–2000 m | Simplified physics, reduced tick rate (e.g., every 4th frame) |
| 2000 m+ | Static or scripted motion only; no dynamic physics |
| Unloaded cylinder | Persistent state stored, no simulation |

Physics integration should use **semi-implicit Euler** or **Verlet** for stability. Rotating-frame pseudoforces are applied as accelerations during integration — not by literally rotating the world.

### Angular Velocity Reference

```
ω = sqrt(g / r) = sqrt(9.81 / 3994.8) ≈ 0.049548 rad/s
Period ≈ 126.8 seconds (~2.1 minutes per revolution)
Rim speed = ωr ≈ 198 m/s
```

### Collision

The exporter emits no collision meshes. Derive them:

- **Buildings** — footprint quad and height are in `manifest.json` per type; instance transform gives placement. Box or extruded-quad colliders are trivial to build at load.
- **Ground and roads** — flat at z ≈ 0 (layer offsets of a few cm are cosmetic, see Rendering).
- **Bridges** — boulevard decks ramp to 6 m over an 80 m run; treat as ramps, not steps.
- **Water** — the river is a flat surface, not a carved channel. Bank geometry below z = 0 does not exist yet.

## Rendering

### Shader-Driven Visual Strategy

The visual strategy prioritizes **shaders over high-resolution textures** to keep memory footprint low and maximize hardware compatibility.

- **Procedural texturing** — noise-based materials for terrain, concrete, vegetation
- **Atmospheric scattering** — simulated atmosphere with haze and distance fog matching the curved interior
- **Central column lighting** — the light column is a massive linear area light; approximate with a multi-sample linear light model
- **Curved horizon rendering** — the ground curves up on all sides; this must feel natural and not produce visual artifacts
- **LOD-aware shading** — distant objects use simpler shaders automatically

### The Curved World Problem

Standard rendering assumes a flat ground plane. In an O'Neill cylinder the ground curves **upward** in every direction, the horizon is **above** the player, and objects overhead are the far side, ~8 km away with an entire city visible.

**Solution: atmospheric fog + a cylindrical backdrop shell.**

- **0–4 km**: No fog. Full geometry at the appropriate LOD tier.
- **4–7 km**: Linear fog ramp. Geometry fades out; impostor tiers live here, so cheapness is masked by haze.
- **7 km+**: Fully fogged. No discrete geometry.

### The Backdrop Shell

Beyond the fog wall, a cylinder mesh carries a baked plan view of the habitat. This replaces the old "regenerate a cylindrical skybox every 30–60 s" plan for static content, though the runtime re-render is still the right mechanism for **lighting changes** (day/night, city lights) — render into a bgfx render target with the same orthographic framing and swap the texture.

| Property | Value |
|---|---|
| Mesh radius | 3,994.8 − 48 ≈ **3,947 m** (the rooftop shell, so parallax displaces away from the viewer) |
| Colour plate | orthographic plan render, exact metric framing, U wraps seamlessly |
| Resolution | 8,192 px across 25.1 km ≈ 3 m/px (parity with 4K at 8 km); 16,384 for headroom |
| Height map | single channel, 16-bit, linear, **1.0 = 112 m**, non-colour data |
| UVs | `u = x / 25100` (repeat), `v = y / 32000` (clamp) |
| Shader | parallax occlusion mapping, depth = `1.0 - height` |

Notes that will save time:

- Sample the height map with an **explicit LOD**; automatic mip selection fights the raymarch at grazing angles.
- POM restores interior parallax (streets read as recessed, courtyards as holes) but **not silhouettes** — the skyline at the visible edge stays a flat cut, so let fog or a band of real LOD2/LOD3 geometry cover the transition.
- Flipping the cylinder's normals inward mirrors the texture; flip U or the image and verify against a known landmark.
- **On rebase, rotate the backdrop, do not translate it.** Shifting by *k* columns means rotating about the axis by `k × 7.2°`, or offsetting U by `k × 0.02`.
- The height ceiling is 112 m because large monuments reach ~106 m. If the monument spec changes, rebake — the old normalization would clip domes flat.

### Level of Detail Policy

| Distance | Geometry | Shading | Shadows |
|---|---|---|---|
| 0–100 m | Prototype LOD0 (full facade, courtyard interior, passage) | Full PBR + detail maps | Full casting/receiving |
| 100–600 m | LOD1 (facade planes, normal-mapped, courtyard kept) | Simplified PBR | Receiving only |
| 600–2500 m | LOD2 (solid massing, courtyard filled, roof shape kept) | Flat shading | None |
| 2.5–4 km | LOD3 (box, ~12 tris) or merged per-chunk batch | Baked colour | None |
| 4 km+ | Backdrop shell only | Fog blend | None |

Chunks pick one LOD level for all their buildings; per-instance LOD selection is not worth the sort churn at these distances.

### Draw Call Budget

The fog radius holds far too many chunks to draw individually at full fidelity (7 km ≈ 613 chunks). The working budget:

| Band | Chunks | Per chunk | Draws |
|---|---|---|---|
| 0–2 km | ~50 | 1 terrain + ≤20 instanced building draws | ≤1,050 |
| 2–4 km | ~150 | 1 terrain + 1 merged LOD3 batch | ~300 |
| 4 km+ | 0 | backdrop shell | 1 |

That lands inside the < 2,000 target. Instances are sorted by `(type, variant)` at load so each type is a single instanced draw. No non-instanced fallback is needed: bgfx dropped `BGFX_CAPS_INSTANCING` because every backend supports it. The current loader goes further and draws each type once for the whole cylinder — see `src/render/CLAUDE.md`.

## Terrain System

### Chunks, Not Authored Tiles

The interior surface is divided into a grid of **502 m × 500 m chunks**: 50 columns around the circumference × 64 rows along the axis = **3,200 chunks** per cylinder. The 502 m column width is what makes 50 columns close the circumference exactly.

Earlier drafts described a library of hand-authored 500 m tiles referenced from a TOML index and a CSV layout grid. That approach is **superseded for generated regions**: chunk terrain is now produced by the generator and exported as mesh data directly, because the city's road network is continuous and does not decompose into a small set of mating tiles. The tile library remains a reasonable mechanism for **hand-authored set pieces** (story locations, the cylinder end caps, docking infrastructure) dropped in over generated terrain, using the original tile-authoring conventions (flat-authored mesh, uniform edge elevation, ~20m internal resolution).

Each chunk file contains:

- a **terrain mesh** — ground, parks, water, islands, roads, bridge decks, roundabout roadways and platforms, flat-shaded with material colour packed per vertex
- a **building instance table** — `(type, x, y, z, rot)`, 20 bytes each
- a **monument instance table** — `(size, x, y, z)`, 16 bytes each

All positions are relative to the chunk centre. Measured sizes: ~35 KB per chunk, ~110 MB for the full map, of which the building instances for all ~375k buildings are about 7 MB. Full byte layout: `docs/WORLD_PIPELINE.md`.

### GPU Curvature Strategy

Unchanged in principle — flat-authored geometry is projected onto the cylinder in the vertex shader:

1. **Vertex shader cylindrical projection.** Every ground vertex maps from map space to the cylinder: `theta = x / R`, `pos = (r·cos θ, r·sin θ, y)` with `r = R − z`.
2. **Correct radial normals.** Vertex normals point radially; lighting interpolation carries the illusion of smoothness past the geometric approximation.
3. **Distance-based tessellation** for chunks within ~200 m of the player.

**Required pipeline change (implemented at load time — see `src/world/CLAUDE.md`):** the exported terrain uses large flat polygons — a chunk's ground is a single quad, roads are long ribbons. Projecting four corners of a 502 m quad leaves a flat chord that sags **7.9 m** below the true arc. Before this renders correctly, the exporter must subdivide any terrain polygon edge longer than ~25 m (a 25 m chord deviates 2 cm, imperceptible), or the renderer must tessellate. Subdividing in the exporter is simpler and keeps the vertex shader trivial: a chunk ground becomes roughly 25 × 25 quads, about 1,250 triangles, which is nothing.

**Buildings do not need this.** They are rigid structures standing on a curved floor, which is physically what they are. A 100 m wide building sitting tangent lifts its far corners 0.3 m — correct behaviour for a rigid foundation, not an artifact. Only surfaces that are meant to *follow* the shell get projected per vertex.

### Chunk Streaming

Load chunks within the fog radius, with a preload ring at ~8 km. Column identity wraps `mod 50`. Chunk work splits cleanly: file read and parse on a worker thread, `bgfx::create*Buffer` on the render thread (or a thread owning an `Encoder`).

**Pad chunk bounding volumes by 110 m horizontally** and by the tallest object vertically (40 m buildings, ~106 m monuments). Buildings are assigned to the chunk containing their centroid and are allowed to overhang; tight bounds pop geometry at chunk edges.

### Buildings Are Not Entities

Do **not** create an EnTT entity per building. At ~375k buildings per cylinder that is a pointless load on the registry. Chunks own flat instance arrays; the renderer walks them directly. Only buildings that are *interactive* — enterable, scripted, quest-relevant — get an entity, created on chunk load from an override list keyed by position.

## World Generation

### The Generator

`tools/CityGenerator/paris_city.py` generates the habitat interior. It is deterministic from `SEED`: hubs, boulevards, the river and roundabout sizes are computed for the **entire map** on every run, while streets, buildings and parks are filled in only for the requested `REGION`. Regions generated separately therefore agree with each other, and the map can be built tile by tile.

Generation order, each pass constraining the next:

**1. River.** A helical centreline entering at one 25.1 km edge and leaving at the other, making exactly **5 laps** of the circumference (~183 km of channel). Width varies 50–300 m; where widest (over 270 m), a tapered island occupies the middle 50 m. Meanders are applied perpendicular to the helix direction, which matters — applied in X they would run parallel to the flow and be invisible at this drift angle. The short-wavelength meanders are damped where the river is wide, so no bend is tighter than the bank offset; otherwise the inner bank folds over itself.

**2. Hubs.** Roundabout centres, minimum 707 m apart, each linked to up to 5 neighbours within 1,414 m (500 m / 1 km scaled by √2, half the density of earlier drafts). The hard constraint is that **no boulevard runs within 20° of a cardinal direction**, which rules out hexagonal packing — every hexagonal neighbourhood puts at least one neighbour in a forbidden wedge. The generator therefore starts from a **sheared lattice** whose basis vectors are chosen so that an integer combination equals exactly (25100, 0), making the layout tile in X, then random-walks the hubs, accepting only moves that preserve every constraint. Result on the default seed: 800 hubs, 89% with 5 links, the rest with 3 or 4.

**3. Boulevards.** The k-nearest-neighbour graph over the hubs, bearing-filtered. Edges that would graze the river for more than 900 m (3 × the widest river) are dropped (otherwise a road nearly parallel to the river becomes a kilometre-long viaduct). Hub count is trimmed to a multiple of 50 so roundabout ratios come out exact.

**4. Superblocks.** The planar arrangement of boulevards plus the map border. **7.5%** of superblocks, chosen by a deterministic hash of their centroid, are set aside as parkland — no streets, no buildings, including on the boulevard frontage facing them.

**5. Minor streets.** Within each remaining superblock, streets fan out perpendicular from the longest boulevard at 98 m centreline pitch, then bend after at least 50 m to meet the far boulevard square-on. Streets never cross the river; they stop at the quay and resume on the far bank. Quay streets run along both banks so the riverside gets frontage instead of dead ends. Superblocks over 120 ha (common beside the river, which hubs keep clear of) are first halved by a minor street across their long axis, recursively, since a single fan leaves most of an oversized block empty.

**6. Buildings.** A frontage walk along every street side places buildings from the 20-type catalogue, greedily, with SAT collision against roads, roundabouts, the river, green zones and other buildings.

**7. Parks.** Leftover space is rasterized at 2.5 m, morphologically opened at 5 m (so alleys and sidewalks do not merge into one giant park), and any remaining region over 500 m² becomes green.

| | |
|---|---|

| Green border | 1,000 m at both axial ends; the river passes through |
| Chunk | 502 × 500 m (50 × 64) |

### Roundabouts and Monuments

Three sizes in a fixed **31 : 17 : 2** ratio, which is why the hub count is forced to a multiple of 50:

| Size | Roadway radius | Platform radius | Monument | Count (default seed) |
|---|---|---|---|---|
| S | 45 m | 15 m | gold cylinder, r 1.5 m, h 5 m | 496 |
| M | 70 m | 40 m | gold cylinder, r 3 m, h 10 m | 272 |
| L | 100 m | 70 m | off-white drum r 65 m × 40 m + 65 m hemisphere (~106 m total) | 32 |

Platform height is 1.5 m; monuments sit at z = 1.5. Large roundabouts require clearance from the river and are placed at least ~2.5 km apart, making the 32 domes the natural long-range landmark set for navigation inside the shell.

### Not Yet Generated

The biome targets from earlier drafts (30% water, 20% park, 25% urban, 25% industrial) are **not** met by the current generator, which produces a single continuous city plus one river. Current coverage is roughly 15% green (7.5% reserved superblocks plus riverside and leftover parks), ~4% water, the rest urban.

Planned as later passes, on a coarse biome grid feeding the generator as a mask:

- **Lakes** — Poisson-disk seeds, noise-modulated blob growth, connected to the river
- **Industrial / science districts** — low-frequency noise partition of the urban area, kept off the waterfront
- **Agricultural and forest zones** — one large contiguous forest reserved away from the lake cluster
- **Density variation** — the city is currently uniform; building-height and block-size gradients by district would do a lot

Each of these is a mask applied *before* the hub pass, since hub placement is what everything else derives from.

### Generator Configuration and Modding

Configuration currently lives in a constants block at the top of `paris_city.py` (`SEED`, `MAP_W`, `MAP_H`, `RIVER_LAPS`, `GREEN_ZONE_SHARE`, `ROUNDABOUT_TYPES`, `BUILDING_TYPES`, …). To preserve the modding story from earlier drafts, this block should move into a TOML seed file the script reads. Illustrative shape (field names not final — the constants above are the source of truth until this lands):

```toml
[generator]
seed = 847291
map_w = 25100
map_h = 32000

[river]
laps = 5
width_min = 50

[green]

[roundabouts]

```

The exported `manifest.json` is already the human-readable index: map constants, material palette, the building catalogue with exact footprints, roundabout specs, and the chunk table.

`SEED` selects the world. **Changing it invalidates everything** — chunks, backdrop plate, height map — so pin it in version control next to the exported data.

### Tooling Commands


Run from `tools/CityGenerator/`. Known rough edge: regions exported separately can leave a few overlapping buildings within ~100 m of a tile border (about 5 pairs per 1,000 buildings in the seam band). Export with `pad ≈ 1500 m` and trim when it matters for playable areas; it is invisible in the backdrop bake.

## Entity Component System Design

### Core Principles

- **Components are plain data.** No logic in components.
- **Systems operate on component sets.** All logic lives in systems.
- **Prefer many small components** over few monolithic ones.
- **Tag components** (empty structs) for categorical queries.
- **Static world content is not entities.** Terrain chunks and building instances live in the world layer, not the registry.

### Component Categories

#### Transform & Spatial

```
CylindricalPosition   { double r, theta, z; }
LocalTransform        { mat4 transform; }          // camera-relative, computed each frame
Velocity              { vec3 v_local; }            // in rotating frame
AngularVelocity       { vec3 omega; }
BoundingVolume        { enum type; vec3 extents; }
ChunkRef              { int16_t col, row; }        // owning chunk, col wraps mod 50
```

#### Rendering

```
MeshInstance          { MeshHandle mesh; uint8_t lod_level; }
Material              { MaterialHandle material; }
ShaderOverride        { ShaderHandle shader; }
Impostor              { TextureHandle billboard; }
Visible               { }                           // tag: currently in frustum
```

#### Physics

```
RigidBody             { float mass; float restitution; }
PhysicsLOD            { enum tier; }
StaticBody            { }                           // tag: immovable
GravityAffected       { }                           // tag: subject to centrifugal/Coriolis
```

#### World

```
Building              { uint16_t type; float rot; }  // only for interactive buildings

LightSource           { vec3 color; float intensity; }

```

```

```

| CylinderTransitionSystem | — | On trigger | Serializes persistent state, unloads, loads next |

| PlayerMovementSystem | PlayerTag, CylindricalPosition, Velocity | Per-frame | Walk/run/jump with rotating-frame correction |
| WaterFlowSystem | WaterBody, CylindricalPosition | Every 4 frames | Coriolis-affected flow (radial term dominates on the helical river) |
| LightColumnSystem | CentralColumn | Per-frame | Day/night cycle, light color/intensity |

## Input Abstraction

SDL3 handles raw input. The game uses an **action mapping layer**:

```
enum class Action {
    MoveForward, MoveBackward, StrafeLeft, StrafeRight,
    Jump, Crouch, Sprint,
    Interact, UseItem,
    LookUp, LookDown, LookLeft, LookRight,
    Pause, ToggleMap,
};
```

Input bindings are stored in a configuration file and are remappable at runtime. Support keyboard+mouse and gamepad from the start.

## Cylinder Transition & Persistent State

1. **Serialize** all entities tagged `PersistentState` in the current cylinder to a binary snapshot.
2. **Unload** the current cylinder's chunks, prototypes, backdrop textures, and non-persistent entities.
3. **Load** the target cylinder's `manifest.json`, prototypes, backdrop, and the chunks around the entry point.
4. **Deserialize** persistent state for the target cylinder.
5. **Spawn** the player at the designated entry point.

Each cylinder is a separate generator seed and a separate `assets/world/cylinder_N/` directory. Prototypes can be shared between cylinders if they share an architectural style, or duplicated if not.

The snapshot format should be compact and versioned. Prefer flat binary over JSON.

## Coding Conventions

- **Naming**: `snake_case` for functions and variables, `PascalCase` for types and components, `UPPER_CASE` for constants.
- **Headers**: Use `#pragma once`. Prefer forward declarations over includes.
- **Memory**: Prefer stack allocation and contiguous containers (`std::vector`). Minimize `new`/`delete`. Smart pointers for ownership when heap allocation is necessary.
- **Error handling**: No exceptions. Return codes or `std::optional`.
- **Comments**: Explain *why*, not *what*. Document non-obvious physics formulas.
- **Formatting**: clang-format with a project `.clang-format` file.
- **World data**: never hardcode map constants in C++ — read them from `manifest.json`. The one exception is the wrap width, which is needed before the manifest loads; keep it in a single `constexpr` and assert it matches the manifest at startup.
